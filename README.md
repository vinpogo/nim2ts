# nim2ts

Generate TypeScript type definitions and a typed RPC client from Nim
declarations, and serialize those types to JSON exactly as declared, so a Nim
backend and a TypeScript frontend share one source of truth for their API
contracts.

nim2ts does not depend on an HTTP server or a TypeScript HTTP or query
library: the app connects the two sides with a few lines of its own.

## Usage

```nim
import std/options
import nim2ts

type
  Role* {.ts.} = enum
    admin, member

  User* {.ts.} = object
    id*: int
    name*: string
    email*: Option[string]
    roles*: seq[Role]
```

Every `nim c` writes:

```ts
// Generated by nim2ts. Do not edit by hand.

export type Role = "admin" | "member";

export type User = {
  id: number;
  name: string;
  email: string | null;
  roles: Role[];
};
```

### Output path

The default is `types.ts`, relative to the directory the compiler runs in.
To change it:

```sh
nim c -d:nim2tsOut=../frontend/src/api/types.ts src/server.nim
```

or in `config.nims`:

```nim
switch("define", "nim2tsOut=" & thisDir() & "/../frontend/src/api/types.ts")
```

An empty value, `-d:nim2tsOut=`, writes nothing: useful for test binaries
that compile only some of the types and would otherwise overwrite the file
with them. Compile errors about the declarations are still reported. With
the snippet below, any entry point other than the app's own writes nothing.

```nim
# config.nims: only the app's own build writes the file
when projectName() == "server":
  switch("define", "nim2tsOut=" & thisDir() & "/../frontend/src/api/types.ts")
else:
  switch("define", "nim2tsOut=")
```

## Type mapping

| Nim                                            | TypeScript          |
| ---------------------------------------------- | ------------------- |
| `string`, `char`                               | `string`            |
| `int*`, `uint*`, `float*`, `Natural`, `Positive` | `number`          |
| `bool`                                         | `boolean`           |
| `JsonNode`                                     | `unknown`           |
| `seq[T]`, `array[N, T]`                        | `T[]`               |
| `Option[T]`                                    | `T \| null`         |
| `Option[T]` field with `{.omitNone.}`          | optional field `?: T` |
| `Table[string, V]`, `OrderedTable[string, V]`  | `Record<string, V>` |
| `ref T`, `distinct T`                          | `T`                 |
| `object` / `ref object`                        | object type `{ … }` |
| `object of Base`                               | `type … = Base & { … }` |
| `enum`                                         | union of string literals (uses explicit string values if given) |
| case object (`case kind: K`)                   | discriminated union (see below) |
| `Foo[T]` (generic)                             | `Foo<T>`            |
| any other name                                 | the same name       |

**Rule:** any custom type you reference must also be annotated with `{.ts.}`.
If you forget one, `tsc` on the frontend reports the unknown name.

### Renaming

`{.ts: "Name".}` declares a type under another name in TypeScript, for
example when the Nim name would shadow a TypeScript global:

```nim
type Record* {.ts: "DbRecord".} = object
  id*: int
```

Every reference to `Record` in other `{.ts.}` types and `{.rpc.}` procs then
emits `DbRecord`, wherever it is declared. JSON is unaffected, since type
names are not on the wire. TypeScript names must be unique.

Names follow Nim's identifier rules (`Json_node` is `JsonNode`). A `{.ts.}`
type cannot take a scalar name from the table above, and a generic one not a
container name either, since `Table[K, V]` would read as the table. A
generic parameter cannot hide a type it refers to: in `Box[DbRecord]`, a
field of type `Record` is a compile error, as TypeScript would read
`DbRecord` as the parameter.

### Case objects

A case object becomes the intersection of its shared fields and one union per
`case` section. Each union member carries the discriminator and exactly the
fields `std/json` emits for that branch:

```nim
type
  ShapeKind* {.ts.} = enum
    circle, rect = "RECT", dot

  Shape* {.ts.} = object
    name*: string
    case kind*: ShapeKind
    of circle:
      radius*: float
    of rect:
      width*, height*: float
    else:
      discard
```

```ts
export type Shape = {
  name: string;
} & (
  | { kind: "circle"; radius: number }
  | { kind: "RECT"; width: number; height: number }
  | { kind: "dot" }
);
```

The discriminator must be a `bool` or an enum annotated with `{.ts.}` and
declared before the case object, so its wire values are known. Two members of
an annotated enum cannot share a string value: the wire could not tell them
apart. Branch labels
must be plain members (no ranges), and nested `case` sections are not
supported yet.

## JSON

`toJson` and `fromJson` (re-exported by `nim2ts`, using only `std/json`)
read the same declarations as the generator, so the JSON always has the shape
of the generated TypeScript:

```nim
let user = fromJson(parseJson(body), User) # raises WireError on bad input
echo toJson(user)
```

- Keys are the Nim field names; there is no renaming.
- A case object writes its discriminator and the fields of the active branch.
- `Option[T]` writes `null` for `none`. Mark the field `{.omitNone.}` to leave
  the key out instead; TypeScript then gets `field?: T`. Reading accepts a
  missing key or `null` as `none` either way.
- A `nil` ref cannot be written, since its TypeScript type has no `null`; use
  `Option` for values that may be missing.
- Integers must stay within JavaScript's safe range, ±(2^53 − 1): beyond it a
  `number` silently loses precision. Writing a larger value raises
  `WireError`, and reading one is rejected; keep bigger ids in a string type.
  `NaN` and infinities have no JSON form and raise `WireError` too.
- `fromJson` is strict: missing keys, wrong JSON kinds, unknown enum values,
  integers out of range (`Natural`, `uint8`, …), arrays of the wrong length
  and strings that are not one `char` raise `WireError`. Its `path` names the
  offending value, as `$.items[2].name`. Unknown keys are ignored.

`std/json`'s own `%` and `to` are not a substitute: `%` cannot write `char`
or distinct types, and `to` silently wraps or pads values that do not fit.

## RPC

Annotate procs with `{.rpc.}`:

```nim
type Db = ref object # yours; not on the wire

proc getUser*(db {.context.}: Db, id: UserId): User {.rpc.} =
  db.find(id)

proc listUsers*(db {.context.}: Db, role: Option[Role]): seq[User] {.rpc.} =
  db.list(role)
```

The generated file gains:

```ts
export type Procedures = {
  getUser: { input: { id: UserId }; output: User };
  listUsers: { input: { role?: Role | null }; output: User[] };
};

export type Transport = <P extends keyof Procedures>(
  procedure: P,
  input: Procedures[P]["input"],
) => Promise<Procedures[P]["output"]>;

export const createClient = (transport: Transport) => ({ … });

export type Client = ReturnType<typeof createClient>;
```

A call is a procedure name and a JSON object holding its parameters; the
answer is the JSON of its result (`null` for a proc without one). How that
travels is the app's choice. On the server, `dispatch` makes the call:

```nim
# e.g. in a handler for POST /rpc/<procedure>
let output = dispatch(procedure, parseJson(request.body), db)
```

and in the browser, a `Transport` sends it:

```ts
const client = createClient(async (procedure, input) => {
  const response = await fetch(`/rpc/${procedure}`, {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(input),
  });
  if (!response.ok) throw new Error(await response.text());
  return response.json();
});

const user = await client.getUser({ id: 1 }); // typed as User
```

- Parameters are read with `fromJson`, results written with `toJson`, so
  every JSON rule above applies. `Option` parameters may be left out.
- A `{.context.}` parameter is not on the wire: it receives the value passed
  as `dispatch`'s third argument, such as a database handle or the current
  user. A proc takes at most one; `dispatch` without a context does not
  compile while any proc needs one.
- `dispatch` raises `WireError` for invalid input and `UnknownProcedure` for
  an unknown name. Whatever the proc raises passes through, so the app decides
  how errors look on the wire, and can declare that shape with `{.ts.}`.
- `dispatch` expands to a `case` over the procs registered so far in the
  compilation. It reaches them whatever its caller imports, but an `{.rpc.}`
  proc compiled after it is a compile error.
- Procedure names are unique across the program (by Nim's identifier rules:
  `fooBar` and `foo_bar` are the same name), generic procs and `var`
  parameters are not supported, and parameters cannot have defaults (use
  `Option[T]`). With any `{.rpc.}` proc, the names `Procedures`, `Transport`,
  `createClient` and `Client` are taken in the generated file.

## How it works

- `type X {.ts.} = ...` is a *type macro pragma*: Nim calls the `ts` macro
  with the untyped `nnkTypeDef` AST and uses whatever it returns (here, the
  unchanged type).
- `src/nim2ts/wire.nim` is the JSON side: generic procs that walk the typed
  values with `fieldPairs` and find `{.omitNone.}` in the type's declaration,
  through inherited fields too.
- `src/nim2ts/convert.nim` turns that AST into TypeScript text. It works on
  syntax only, so it maps type *names*. `toTsType` is where new mappings go.
- `src/nim2ts.nim` keeps compile-time lists of all declarations, their
  TypeScript names, the wire values of every annotated enum (case object
  branches need them) and the `{.rpc.}` procs. It renders and rewrites the
  whole output file on every `{.ts.}` and `{.rpc.}`; the last one leaves the
  complete file behind. Under `nim check` and nimsuggest, `writeFile` is a
  no-op, so your editor won't touch the file.
- `proc foo(...) {.rpc.}` is a proc macro pragma. It keeps the proc and adds
  a wrapper that reads the parameters into a hidden object type and writes
  the result. The wrapper's symbol is stored with `std/macrocache`, and
  `dispatch` calls those symbols directly.

To see the AST of any Nim snippet, wrap it in `dumpTree:` from `std/macros`.

## Tests

```sh
nimble test
```

- `tests/tconvert.nim` unit-tests the mapping at compile time.
- `tests/tgenerate.nim` compares the generated file to `tests/expected.ts`.
  The files in `tests/json/` are values of those types, written by hand from
  the TypeScript type each is named after: `toJson` must write exactly that
  and `fromJson` read it back. The files in `tests/rpc/` are calls of its
  `{.rpc.}` procs, which `dispatch` must answer with the expected output. Its
  types include deliberate combinations of features, so a new feature should
  get one there too, with JSON files for it.
- `tests/twire.nim` tests the JSON rules.
- `tests/tcompile.nim` checks behavior across modules and the compile
  errors in `tests/fixtures/`.

When the TypeScript changes on purpose, review the diff and copy
`tests/generated.ts` over `tests/expected.ts`, then update the JSON files
the change affects.
CI runs the same on every pull request.
